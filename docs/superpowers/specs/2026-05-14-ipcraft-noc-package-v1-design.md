# Ipcraft NoC Package V1 Design

## Summary

Ipcraft NoC Package V1 defines the public package contract for adapting NoC IPs to the editor. The goal is that a new NoC IP can be edited, validated, and generated by publishing a compliant package, without modifying the Qt frontend or the main repository.

The package format is centered on a human-authored `ipcore.yml`, XML view files, a generated runtime manifest, and optional Qt dynamic plugins. The NoC package schema remains NoC-oriented for the frontend, while every interface, mode, and connection class must be mappable to IP-XACT connection semantics. A real IP-XACT file is optional; when provided, it is used only for strict connection checking.

## Goals

- Support NoC IP creation as the V1 product scope.
- Allow adapting more NoC IPs by publishing packages instead of changing Qt code.
- Keep authoring approachable through a constrained YAML source format and XML views.
- Keep Qt runtime parsing simple by consuming a normalized manifest rather than raw YAML.
- Preserve `interface` as the shared concept between the frontend and IP-XACT `busInterface`.
- Allow frontend fast connection checks through `connection_classes`.
- Require every interface, mode, and connection class to map to IP-XACT connection semantics.
- Make IP-XACT files optional, while enabling strict connection checks when they exist.
- Keep Qt dynamic plugins separate from schema extensions.
- Declare command input project schema versions explicitly.

## Non-Goals

- Do not support arbitrary non-NoC IP package behavior in V1.
- Do not make IP-XACT files mandatory for basic package use.
- Do not make the frontend run full IP-XACT validation on every drag operation.
- Do not make `connection_classes` a replacement for IP-XACT.
- Do not use committed `generated/ipcores` runtime bundles as the long-term package model.
- Do not put view, topology, collapse, attachment, or command semantics into IP-XACT strict checks.
- Do not use `finepaper` in public schema names, file names, or project schema names.

## Architecture

V1 has four layers.

The authoring layer contains `ipcore.yml` and `views/*.xml`. The YAML file is a constrained, human-writable source format. View XML describes presentation only: shapes, states, anchors, attachment zones, and collapsed or expanded visual behavior.

The package build layer is `specgen`, exposed as an IP developer CLI. It validates `ipcore.yml`, loads enabled schema extensions, expands extension modes and defaults, checks IP-XACT connection semantic mappability, and writes the runtime manifest.

The runtime layer is a package directory consumed by Qt. Qt reads the runtime manifest and XML views, not raw authoring YAML. Runtime packages may include generator and validator commands, optional IP-XACT files, optional Qt dynamic plugins, and package-local vendor content.

The built-in Qt validation layer checks all editor-owned invariants: package structure, project references, graph ownership, view references, topology preset inputs, connection fast rules, command declarations, and IP-XACT connection mappings. IP-XACT strict checks are a narrower optional sub-pass. When an IP-XACT file is present, that sub-pass compares project interconnections against IP-XACT connection semantics. When no IP-XACT file is present, `specgen` still requires the package schema to carry enough mapping information for every interface, mode, and connection class to map to IP-XACT connection semantics.

Qt has a runtime responsibility in this design, not just a file-loading responsibility. It must load packages, build the module and interface catalog, map project references back to package metadata, run frontend fast connection checks, surface warnings in the log panel, and pass schema-versioned project JSON to external commands. It must not parse authoring YAML in the normal runtime path.

## Package Layout

A source package may contain:

```text
<package>/
  ipcore.yml
  ipcraft.json
  views/
  tools/
  ipxact/
  plugins/
  vendor/
  docs/
  examples/
```

Only `ipcraft.json`, referenced view files, and declared command paths are required at runtime. `ipcore.yml` is the recommended source of truth for open packages, but the runtime loader does not require it.

## Public Names

Public schema names use `ipcraft`, not the product legacy name.

```text
ipcraft.package.v1
ipcraft.manifest.v1
ipcraft.noc.project.v1
```

The runtime manifest file is:

```text
ipcraft.json
```

## Authoring YAML

The source YAML uses a constrained subset. This subset is part of the public contract because YAML has features that are convenient for authors but risky for predictable schema validation.

- no YAML anchors;
- no aliases;
- no merge keys;
- no custom tags;
- no multi-document streams;
- no implicit timestamp parsing;
- no duplicate mapping keys;
- explicit schema version;
- stable IDs for referenced objects;
- unknown keys are errors unless they live under a documented extension namespace;
- lists of named objects must use explicit `id`;
- modes must be IP-XACT-native modes or extension-defined modes with a mapping.

Scalar parsing rules:

- strings are strings unless a field schema declares another type;
- booleans must be `true` or `false`;
- integers must be base-10 digits with an optional leading minus sign;
- version values are strings, even when they look numeric;
- width and parameter expressions are strings when they reference parameters;
- null values are not accepted in required fields.

`specgen` is the only component that must parse authoring YAML. Qt runtime consumes the normalized manifest.

Example:

```yaml
schema: ipcraft.package.v1
id: org.example.opennoc
name: OpenNoC
version: 1.0.0

extensions:
  noc.v1:
    enabled: true
    features:
      chi_mapping: true
      attachment: true
      mesh_topology: true

ipxact:
  root: ipxact/component.xml
  generated: false

connection_classes:
  - id: chi_node_interface
    roles: [node, interconnect]
    symmetric: false

  - id: chi_peer_link
    roles: [peer, peer]
    symmetric: true

modules:
  - id: xp
    name: XP
    graph_role: host
    interfaces:
      - id: rnf0
        modes: [chi_interconnect]
        accepts:
          - class: chi_node_interface
            role: interconnect
        multi_connection: false
        ipxact:
          bus_interface: rnf0

  - id: rnf
    name: RNF
    graph_role: attached
    attach:
      hosts: [xp]
      zone: rnf
    interfaces:
      - id: chi
        modes: [chi_requester_node]
        accepts:
          - class: chi_node_interface
            role: node
        multi_connection: false
        ipxact:
          bus_interface: chi

views:
  - module: xp
    file: views/OpenNoCXP.xml

commands:
  validate:
    executable: tools/validate
    input_schema: ipcraft.noc.project.v1

  generate:
    executable: tools/generate
    input_schema: ipcraft.noc.project.v1
```

## Runtime Manifest

`specgen` writes `ipcraft.json`. The manifest is normalized for Qt:

- extension modes are expanded;
- default extension-provided mappings are materialized;
- all referenced views and commands are resolved relative to the package root;
- interface accept rules are ready for frontend fast checks;
- optional IP-XACT roots are recorded when present.

Qt does not need to parse authoring YAML to edit a project.

The manifest must be strict JSON:

- duplicate object keys are invalid;
- unknown required-shape fields are invalid unless they are under a documented extension namespace;
- all relative paths are relative to the package root;
- all IDs referenced by modules, interfaces, views, commands, topology presets, and extension state must resolve inside the same package.

Qt package loading must reject malformed manifests before registering any partial package.

## Qt Runtime Behavior

Qt loads packages in this order:

1. read package roots from application settings;
2. find `ipcraft.json` in each package root;
3. parse and validate the manifest structure;
4. load enabled runtime-visible extensions known to Qt;
5. register modules, interfaces, connection classes, topology presets, views, commands, and optional plugin metadata;
6. validate that view XML references existing modules and interfaces;
7. expose valid packages in the IP catalog.

Qt must not register a package partially. If package load fails, the IP catalog omits that package and the log panel records the fatal reason.

Qt must maintain these runtime indexes:

- package ID to package descriptor;
- module ID to module descriptor within a package;
- interface ID to interface descriptor within a module;
- connection class ID to class descriptor within a package;
- view module ID to view file path;
- command name to executable and input schema.

Qt must resolve all project references through those indexes:

```text
project instance -> package id + module id
project connection participant -> instance id + interface id
connection class -> package connection class id
```

When a project references a missing package, module, interface, or connection class, Qt keeps the project load error explicit instead of silently replacing it with fallback metadata.

## Qt Built-In Validation

Qt built-in validation runs before package `validate` or `generate` commands. It is the editor's own consistency pass and must not be skipped just because an IP package provides an external validator.

Qt built-in validation checks at least:

- loaded packages are complete and were not partially registered;
- project IP instances reference existing packages and modules;
- graph modules belong to valid project IP instances;
- graph ownership is consistent for package ID and instance ID;
- view XML references existing modules, interfaces, and attachment zones;
- topology preset requests reference existing modules, graph roles, and interfaces;
- commands declare executable paths and input schemas before they can run;
- project connections pass the fast connection rules;
- package metadata remains mappable to IP-XACT connection semantics;
- if an IP-XACT root exists, the IP-XACT connection sub-pass succeeds or reports diagnostics.

Package `validate` commands are an additional DRC layer. They check IP-specific design rules that Qt cannot know, but they do not replace Qt built-in validation.

Generate and Validate actions both run Qt built-in validation first. Generate must stop on built-in validation errors. Validate reports built-in diagnostics and then runs package validators for instances that remain executable.

## Qt Fast Connection Validation

Qt performs a fast connection validation pass during editing. This pass is one part of built-in validation and is separate from optional IP-XACT strict checks and package command validation.

For each attempted connection, Qt checks:

- every participant instance exists;
- every participant interface exists on that instance's module;
- all participants belong to the same package instance scope when the package requires local-only connections;
- the selected connection class exists;
- each participant interface accepts the selected class;
- participant roles match the selected class roles;
- `multi_connection: false` interfaces are not already used by another active connection;
- symmetric classes normalize participant order so reverse drag produces the same connection;
- ambiguous class matches create a warning-state connection with alternatives.

Qt must store project connections using unordered `interfaces`, not `from` and `to`. Drag direction is an input gesture only; it is not saved as connection semantics.

The property panel must expose the selected connection class for warning-state ambiguous connections. The log panel must record invalid or ambiguous connection decisions with enough context for the user to locate the instances and interfaces.

## Qt IP-XACT Mapping And Strict Connection Check

Qt must be able to map loaded package metadata and project connections into IP-XACT connection concepts:

```text
module -> component
interface -> busInterface
project instance -> componentInstance
project connection -> interconnection
connection participant -> activeInterface
```

This mapping is required even when no IP-XACT XML file is provided. Without an IP-XACT root, Qt can still run fast checks and command validation, but it must know that the package manifest was built from mappable metadata.

When an IP-XACT root is provided and the implementation includes an IP-XACT strict checker, the IP-XACT sub-pass checks connection relationships only:

- referenced component instances exist;
- referenced bus interfaces exist;
- interface modes are compatible;
- bus and abstraction definitions are compatible;
- monitor and mirrored interface connection rules are respected where represented;
- multi-participant interconnections follow IP-XACT connection semantics.

The IP-XACT sub-pass does not inspect view layout, topology preset algorithms, graph role behavior, plugin behavior, generator output contents, or RTL correctness. Those editor-owned areas are still covered by Qt built-in validation where applicable.

IP-XACT strict connection findings are diagnostics attached to project connections and shown through the same validation results UI as built-in validation and package command findings.

## Plugin

`plugin` is reserved for Qt dynamic plugins only.

```yaml
plugin:
  library: plugins/libopennoc_qt.so
  entry: OpenNoCPlugin
```

The `plugin` block is optional. If it is absent, the package still loads through standard V1 behavior.

The dynamic plugin is not a schema extension. It may add editor UI, custom panels, specialized diagnostics, or package-specific actions in a future implementation. It must not be required for baseline NoC editing.

## Extensions

`extensions` are schema and `specgen` semantic helpers. They are not Qt dynamic libraries.

V1 includes `noc.v1`. The V1 NoC extension provides:

- CHI mode descriptions and mappings to IP-XACT connection semantics;
- host and attached graph role defaults;
- attachment and mirror-into-host defaults;
- mesh topology preset generation helpers;
- schema validation rules for NoC-specific fields.

V1 does not require the NoC extension to cover AXI authoring shortcuts. AXI may still be represented by IP-XACT-native modes and explicit interface accept rules.

Extension modes are valid only when the declaring extension is enabled. IP-XACT-native modes are valid without an extension.

## Interfaces

`interface` is the core editable connection point. It corresponds to an IP-XACT `busInterface`.

```yaml
interfaces:
  - id: chi
    modes: [chi_requester_node]
    accepts:
      - class: chi_node_interface
        role: node
    multi_connection: false
    ipxact:
      bus_interface: chi
```

Rules:

- `id` is the frontend and project reference.
- `modes` may contain IP-XACT-native modes or enabled extension modes.
- `accepts` lists frontend-fast connection classes and the role this interface can play in each class.
- `multi_connection` controls whether this interface can participate in more than one project connection.
- `ipxact.bus_interface` maps the interface to an IP-XACT `busInterface` name when an IP-XACT document is present or generated.

All interfaces must be mappable to IP-XACT connection semantics, even when no IP-XACT file is packaged.

## IP-XACT Connection Mapping

Each interface and connection class must have one mapping source:

- an IP-XACT-native mode such as `initiator`, `target`, `system`, `mirroredInitiator`, `mirroredTarget`, `mirroredSystem`, or `monitor`;
- an enabled extension mode that expands to IP-XACT connection semantics;
- explicit package metadata under `ipxact` fields.

`specgen` rejects a package when any interface mode or connection class cannot be resolved through one of these sources.

This mapping requirement exists even when the package does not include an IP-XACT XML file. The XML file controls whether strict connection checks can use a concrete IP-XACT document; it does not control whether package semantics must be compatible with IP-XACT connection concepts.

## Connection Classes

`connection_classes` are a frontend fast-check model.

```yaml
connection_classes:
  - id: chi_node_interface
    roles: [node, interconnect]
    symmetric: false
```

They let the editor quickly answer:

- whether two or more interfaces have a compatible class;
- whether their roles satisfy the class;
- whether drag direction matters;
- whether a warning state is needed because multiple legal classes exist.

`connection_classes` are not an IP-XACT replacement. `specgen` must verify that every class can map to IP-XACT connection semantics.

If two interfaces share more than one legal class, the editor creates a warning-state connection using a deterministic default. The property panel exposes the selected class, and the log panel records the ambiguity and alternatives. The connection remains editable until the user selects the intended class.

## Modules And Graph Roles

Modules describe editor-creatable NoC graph objects.

```yaml
modules:
  - id: xp
    name: XP
    graph_role: host
    interfaces: []

  - id: rnf
    name: RNF
    graph_role: attached
    attach:
      hosts: [xp]
      zone: rnf
    interfaces: []
```

V1 graph roles are:

- `host`: a core graph node that can own attachment zones;
- `attached`: a node that attaches to a host zone and may collapse into the host visual;
- `standalone`: a normal graph node with no host or attached behavior.

Graph roles are editor semantics. They are not part of IP-XACT strict connection checks.

## View XML

View XML describes presentation. It references modules and interfaces from the manifest.

View XML may describe:

- shapes;
- expanded or collapsed states;
- interface anchors;
- attachment zone anchors;
- captions and labels;
- mirror behavior for attached nodes.

View XML must not define bus semantics, connection legality, generator commands, or IP-XACT mapping.

## Project Connections

Project files use unordered interface participants, not `from` and `to`.

```json
{
  "id": "conn_0",
  "class": "chi_node_interface",
  "interfaces": [
    { "instance": "rnf_0", "interface": "chi" },
    { "instance": "xp_0", "interface": "rnf0" }
  ],
  "status": "valid"
}
```

This maps to IP-XACT design interconnections:

```text
instance + interface
=> componentInstanceRef + busInterfaceRef
=> interconnection/activeInterface
```

Ambiguous connections use warning status:

```json
{
  "id": "conn_1",
  "class": "chi_node_interface",
  "interfaces": [
    { "instance": "a", "interface": "x" },
    { "instance": "b", "interface": "y" }
  ],
  "status": "ambiguous",
  "alternatives": ["chi_node_interface", "monitor_tap"]
}
```

The property panel must allow changing `class`. The log panel must record the ambiguity and available alternatives.

## IP-XACT

The `ipxact` block is optional.

```yaml
ipxact:
  root: ipxact/component.xml
  generated: false
```

If an IP-XACT root is present:

- strict checks use the IP-XACT document for connection compatibility;
- the IP-XACT sub-pass covers connections only;
- Qt built-in validation still covers package, project, view, topology, command, graph role, and fast connection rules.

If no IP-XACT root is present:

- normal editing still works;
- frontend fast checks still use `connection_classes`;
- package validate and generate commands can still run;
- Qt built-in validation still checks all editor-owned package and project rules;
- `specgen` still requires all interfaces, modes, and connection classes to be mappable to IP-XACT connection semantics.

## Commands

Commands declare their input project schema.

```yaml
commands:
  validate:
    executable: tools/validate
    input_schema: ipcraft.noc.project.v1

  generate:
    executable: tools/generate
    input_schema: ipcraft.noc.project.v1
```

The project JSON passed to commands must contain:

```json
{
  "schema": "ipcraft.noc.project.v1",
  "package": "org.example.opennoc",
  "instances": [],
  "connections": []
}
```

`validate` and `generate` are package commands. They are not IP-XACT TGI support in V1. Qt runs built-in validation before invoking either command.

## Topology Presets

Topology presets are NoC extension behavior. They may create mesh-style or other package-declared graph structures without hardcoding RaveNoC or OpenNoC behavior in Qt.

Preset creation must use manifest-defined modules, interfaces, graph roles, attachment zones, and connection classes. It must not depend on hardcoded names such as `east`, `west`, `ep`, or `local`.

## Specgen

`specgen` is an IP developer CLI, not a repository-local generator of committed runtime bundles.

It must support:

- checking `ipcore.yml`;
- building `ipcraft.json`;
- loading schema extensions;
- expanding extension modes and defaults;
- validating that every mode is IP-XACT-native or extension-defined;
- validating that every interface, mode, and connection class maps to IP-XACT connection semantics;
- validating that view XML references existing modules and interfaces;
- validating that command input schemas are declared;
- optionally generating or checking IP-XACT files.

## Error Handling

Package load errors are fatal when:

- `ipcraft.json` is missing or malformed;
- schema names are unsupported;
- a module references a missing interface, class, view, or attachment target;
- an interface uses a mode that is neither IP-XACT-native nor provided by an enabled extension;
- an interface accept rule references a missing connection class;
- a command omits `input_schema`;
- a view references a missing module or interface.

Package load warnings are allowed when:

- a Qt dynamic plugin is declared but unavailable and the package can still run through baseline behavior;
- an optional IP-XACT root is absent;
- a project connection has multiple legal classes and has not yet been resolved by the user.

## Testing

The implementation should prove:

- a package can load without an IP-XACT file;
- package metadata can still map all interfaces, modes, and connection classes to IP-XACT connection semantics;
- Qt built-in validation runs before package validate and generate commands;
- `plugin` and `extensions` are parsed as distinct concepts;
- `interface` references are used in project connections;
- reverse drag creates the same unordered connection as forward drag;
- ambiguous connection classes create warning status and log panel entries;
- commands reject missing input schema declarations;
- view XML references are checked against modules and interfaces;
- NoC extension CHI modes expand into valid IP-XACT connection semantic mappings;
- Qt does not discover concrete IPs from a committed `generated/ipcores` directory as the long-term package path.

## Deferred Decisions

- Package discovery will support user-added package directories through application settings in V1. A shared install location can be added later without changing package schema.
- The exact XML element names for view anchors and attachment zones belong to a follow-up view schema document. This package spec only requires that view XML references manifest modules and interfaces.
- The dynamic Qt plugin ABI is deferred. V1 preserves the `plugin` metadata block but baseline NoC editing must not depend on loading a dynamic plugin.
