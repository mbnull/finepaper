# Ipcraft NoC Black-Box Validation Guide

## Purpose

This document is the complete public contract for a third-party validation agent. The agent will independently write test code and perform black-box validation. The agent must not depend on repository implementation code, internal unit tests, private review notes, or private conversation context.

The goal is to validate whether NoC package support is usable through public inputs and observable outputs:

- package source files supplied by the test;
- the `spec-gen` command;
- the Qt frontend UI;
- the `ipcraft-generate` command;
- generated files, logs, stdout, stderr, and process exit codes.

## Access Model

The validation agent may use:

- this document;
- built or packaged binaries/scripts exposed as public tools;
- user-visible Qt UI behavior;
- files generated by the public tools during the validation run;
- package source fixtures written by the validation agent from this document;
- public runtime artifacts produced from those fixtures, such as `ipcraft.json` and generated output directories.

The validation agent must not use:

- existing repository test code;
- implementation source code;
- internal helper classes, private APIs, or private C++/Ruby functions;
- private conversation history;
- undocumented assumptions from current implementation details.

If a validation step cannot be performed without reading implementation code or existing tests, the step is underspecified and should be reported as a documentation gap.

## Public Tool Contracts

### `spec-gen`

Purpose: validate package source and build runtime manifests.

Required commands:

```bash
spec-gen build --ipcore <package-root>/ipcore.yml --package-root <package-root>
spec-gen check --ipcore <package-root>/ipcore.yml --package-root <package-root>
```

Expected behavior:

- `build` exits 0 for a valid package and writes `<package-root>/ipcraft.json`.
- `check` exits 0 when the existing `<package-root>/ipcraft.json` matches the generated manifest.
- `check` exits nonzero when `ipcraft.json` is missing or does not match the package source.
- malformed package source exits nonzero and prints an actionable error to stderr.
- generated `ipcraft.json` is deterministic for the same package source.

### Qt Frontend

Purpose: load runtime packages, let users create/edit NoC graphs, export command input, and run package commands.

Required user-visible behavior:

- There is a visible UI path for managing IP package roots. The expected menu label is `Tools -> IP Core Packages...`.
- The package-root UI supports adding, removing, persisting, and reloading package roots without restarting.
- Loading one invalid package must not prevent unrelated valid packages from loading.
- Duplicate package IDs must produce a visible diagnostic instead of silently selecting one package.
- The catalog, node labels, connection choices, topology presets, command logs, and generated output paths must use user-facing names where documented below.

### `ipcraft-generate`

Purpose: generate package outputs from a runtime manifest and exported command input.

Required command:

```bash
ipcraft-generate --manifest <package-root>/ipcraft.json --input <command-input.json> --output <output-dir>
```

Expected behavior:

- The command exits 0 for a valid manifest and valid `ipcraft.noc.project.v1` input.
- The command writes a generation `manifest.json` in the output directory.
- The command exits nonzero for mismatched package IDs, unknown instance references, unknown interface references, invalid graph shape, or unsupported schema.
- On failure, the command must not present partial output as a successful generation result.

## Package Source Contract

A NoC package source root contains:

```text
<package-root>/
  ipcore.yml
  views/
    <module-view>.xml
```

`ipcore.yml` must use:

```yaml
schema: ipcraft.package.v1
```

The validation agent should treat these as public package authoring concepts:

- package identity: `id`, `name`, `version`;
- modules with stable module IDs;
- module parameters;
- display bindings through `display.label_parameter` and `display.short_label_parameter`;
- interfaces with labels, modes, connection accepts, and optional topology metadata;
- connection classes;
- view XML files referenced by module;
- topology presets;
- generation metadata;
- commands using either package-local `executable` or framework-owned `framework_tool`.

The public runtime manifest generated by `spec-gen` must use:

```json
{ "schema": "ipcraft.manifest.v1" }
```

## Command Input Contract

Qt commands that declare NoC command input must export JSON with:

```json
{ "schema": "ipcraft.noc.project.v1" }
```

The command input must contain enough black-box observable design state for generation:

- package ID;
- project or design identity;
- IP instance identity;
- module instances;
- stable instance IDs;
- manifest module IDs;
- module parameters, including display-name parameters when present;
- interfaces;
- connections;
- selected connection class;
- normalized endpoint references.

Display text is not identity. Tests should verify that generators can identify modules and interfaces without relying on display names.

## Supported NoC Behaviors

The validation agent should verify these behaviors as supported.

1. Package source of truth
   - `ipcore.yml` plus `views/*.xml` can produce `ipcraft.json`.
   - `ipcraft.json` drift is detected by `spec-gen check`.
   - malformed YAML, invalid references, and unsafe paths fail with diagnostics.

2. Package discovery UX
   - A clean frontend can start with no loaded package roots.
   - The user can discover where to add package roots.
   - Adding a package root loads valid packages and shows diagnostics for invalid packages.
   - Removing a root and reloading removes those packages from the catalog.
   - Package roots persist across app restart.

3. Display and connection UX
   - Canvas node captions use declared display-label parameters when available.
   - Static module names or labels are used only when no display binding is declared.
   - Connection choices use display names and interface labels.
   - Internal IDs, UUIDs, or raw runtime IDs are only acceptable as final debug disambiguation.
   - Duplicate display names use short labels before debug IDs.

4. Topology metadata
   - NoC topology behavior is driven by package metadata, not by package ID.
   - Interface IDs do not have to be named `north`, `east`, `south`, or `west` if topology metadata declares the meaning.
   - `opposite_side` and explicit opposite-interface metadata are enforced when connecting topology links.
   - Presets can instantiate tested mesh/ring layouts from metadata.

5. Command input and generation
   - Validate/generate commands receive `ipcraft.noc.project.v1` when declared.
   - The exported command input is separate from the saved project document.
   - Generated command-input filenames and logs should not describe the command input as a saved project file.
   - Packages can route generation through `framework_tool: ipcraft-generate`.
   - Framework tool resolution must not depend on the process current working directory.

6. Existing package compatibility
   - `finepaper-noc`, `opennoc`, and `ravenoc` remain loadable through package roots.
   - The common generation path produces key package outputs for those packages.
   - Missing proprietary or vendor assets should be reported as environment limitations unless the specific test includes those assets.

## Black-Box Fixture Requirements

The validation agent should write its own fixtures. Do not copy existing repository tests.

At minimum, create these package fixtures.

### Fixture A: Valid Synthetic NoC

Purpose: prove a metadata-only NoC package can be loaded and exercised without implementation-specific knowledge.

Required package ID:

```text
blackbox.synthetic.noc
```

Required modules:

- `Tile`
- `Endpoint`

Required display behavior:

- `Tile` has `display_name` and `external_id` parameters.
- `Tile.display.label_parameter` is `display_name`.
- `Tile.display.short_label_parameter` is `external_id`.
- `Endpoint` has the same display bindings.

Required interface behavior:

- `Tile` has four fabric interfaces whose IDs are not cardinal-direction names. Example IDs:
  - `fabric_a_out`
  - `fabric_a_in`
  - `fabric_b_out`
  - `fabric_b_in`
- Those interfaces declare topology metadata for side/opposite behavior.
- `Endpoint` has one local NoC interface.

Required topology behavior:

- One `mesh` topology preset using `Tile`.
- Preset dimensions include `rows` and `cols`.
- The preset must be usable from Qt to create at least a 2x2 mesh.

Required generation behavior:

- `generation.engine` is `ipcraft.common.v1`.
- The package declares outputs including `manifest.json`.
- The `generate` command uses:

```yaml
framework_tool: ipcraft-generate
input_schema: ipcraft.noc.project.v1
args: ["--manifest", "{manifest}", "--input", "{input}", "--output", "{output}"]
```

Required views:

- `views/Tile.xml` references every `Tile` interface by `anchor ref`.
- `views/Endpoint.xml` references the endpoint interface by `anchor ref`.
- View labels are human-readable and do not have to match interface IDs.

Acceptance:

- `spec-gen build` succeeds.
- `spec-gen check` succeeds after build.
- Qt loads the package from a configured root.
- The package appears in the catalog.
- A 2x2 mesh can be created.
- Node captions use display names.
- Connection options use display and interface labels.
- Generation writes output `manifest.json`.

### Fixture B: Invalid Package Mixed With Valid Package

Purpose: prove one malformed package does not block a valid package in the same configured root set.

Create:

- one copy of Fixture A;
- one package with a unique package ID but a malformed view reference, such as an anchor pointing to an unknown interface.

Acceptance:

- Qt reports a diagnostic for the malformed package.
- Fixture A still loads.
- Fixture A can still create topology presets and run commands.

### Fixture C: Duplicate Package IDs

Purpose: prove duplicate package IDs do not silently select one package.

Create two valid package roots with the same package ID and different names.

Acceptance:

- Qt reports a duplicate package ID diagnostic.
- The duplicate package is not silently selected as if unambiguous.
- Unrelated packages still load.

### Fixture D: Invalid Command Input

Purpose: prove generation validates black-box command input.

Start from a valid `ipcraft.noc.project.v1` export and create these mutated inputs:

- package ID does not match `ipcraft.json`;
- one connection references an unknown instance;
- one connection references an unknown interface;
- one connection has an invalid endpoint shape;
- one mesh omits a required tile or creates inconsistent coordinates.

Acceptance:

- `ipcraft-generate` exits nonzero for each mutated input.
- stderr names the invalid package, instance, interface, connection, or graph shape closely enough for a package author to fix it.
- no success `manifest.json` is produced for the failed case.

## Required Test Matrix

The validation agent should independently implement tests covering this matrix.

| Area | Test | Expected Result |
| --- | --- | --- |
| Spec build | Build Fixture A | exit 0 and `ipcraft.json` exists |
| Spec drift | Modify generated `ipcraft.json`, then run check | nonzero exit and drift diagnostic |
| Spec validation | Unknown view anchor | nonzero exit and unknown interface diagnostic |
| Package roots | Add Fixture A root in UI | package visible without restart |
| Package roots | Remove Fixture A root and reload | package removed without restart |
| Package roots | Mixed valid/invalid roots | valid loads, invalid reports diagnostic |
| Package roots | Duplicate package IDs | duplicate diagnostic, no silent selection |
| Display labels | Set two different display names | canvas and connection choices show display names |
| Display labels | Duplicate display names with different short labels | short labels disambiguate before debug IDs |
| Topology | Build 2x2 mesh from Fixture A | graph has four tile instances and valid links |
| Topology | Connect explicit non-opposite interfaces | connection rejected with rule diagnostic |
| Command input | Run generate through Qt | command input schema is `ipcraft.noc.project.v1` |
| Command input | Inspect generated command input | identities are stable IDs, display text remains parameter data |
| Generator | Run `ipcraft-generate` from a different current directory | generation succeeds |
| Generator | Feed invalid command input | nonzero exit and no successful output manifest |

## Manual UX Validation

Manual checks are allowed only for behavior that is expensive to automate. Record screenshots or logs for each manual step.

1. Start the Qt frontend with a clean settings profile.
2. Confirm the user can find `Tools -> IP Core Packages...`.
3. Add Fixture A as a package root.
4. Confirm the catalog reloads and diagnostics/logs mention the package load result.
5. Create a 2x2 mesh preset from Fixture A.
6. Rename two nodes through display-name parameters.
7. Open a connection selection UI and confirm it shows display/interface labels rather than UUIDs.
8. Run a generate command.
9. Confirm the command input is described as command input, not as a saved project file.
10. Restart the app and confirm the package root persisted.

## Existing Package Compatibility Checks

The validation agent may be given packaged versions of the three existing NoC packages as public black-box inputs:

- `finepaper-noc`
- `opennoc`
- `ravenoc`

For each package, validate only through public tools and UI:

- `spec-gen build` succeeds from its package source bundle.
- `spec-gen check` succeeds after build.
- Qt loads the package from a configured root.
- At least one documented topology preset or basic graph can be created.
- Generate command routes through the public framework tool path where declared.
- The output directory contains a generation `manifest.json`.

Do not require unavailable vendor or proprietary assets unless those assets are explicitly provided to the validation environment.

## Non-Scope For This Validation

Do not reject the implementation for:

- arbitrary free-form topology placement;
- a general-purpose generation scripting language;
- byte-for-byte matching of timestamps, comments, or non-semantic formatting;
- removing all legacy fallback behavior;
- redesigning the saved project file format;
- support for undocumented schema fields;
- private vendor tool flows when vendor assets are not provided.

If Fixture A requires Qt implementation changes for behavior described in this document, classify it as a supported-behavior regression or schema gap. If a desired behavior is not described in this document, classify it as future scope.

## Failure Classification

Every failure should be classified as one of:

- `REGRESSION`: documented supported behavior fails through public tools or UI.
- `DOC_GAP`: the document lacks enough detail to write a black-box test.
- `SCHEMA_GAP`: the desired generic NoC behavior cannot be expressed with documented package metadata.
- `ENVIRONMENT_GAP`: the environment lacks required public tools or explicitly provided vendor assets.
- `FUTURE_SCOPE`: the behavior is useful but outside this validation contract.

## Required Report Format

The final third-party report should include:

- tool versions or build identifiers provided by the validation environment;
- package fixtures created by the validation agent;
- commands executed;
- UI flows exercised;
- generated files inspected;
- failures with classification and reproduction steps;
- whether Fixture A was loadable and usable without implementation-code access;
- whether the three existing NoC packages passed public compatibility checks if they were provided.

The final verdict must be one of:

- `APPROVED`: all required black-box tests pass.
- `APPROVED_WITH_GAPS`: no regression was found, but `DOC_GAP`, `SCHEMA_GAP`, or `ENVIRONMENT_GAP` items remain.
- `REJECTED`: at least one `REGRESSION` was found.
